SmartTicket: venta y control de entradas para eventos

Sistema organizado en etapas para cotizar entradas, procesar pagos simulados, emitir entradas y validar el acceso a eventos musicales.

Tipo: Sistema académico de gestión de entradas
Enfoque: Programación orientada a objetos, GRASP y SOLID
Tecnologías: FastAPI, SQLAlchemy y SQLite

1. Contexto

SmartTicket es un proyecto académico de gestión de venta y control de entradas para eventos musicales. El dominio del sistema contempla lugares, sectores, eventos, clientes, ventas y entradas.

El repositorio organiza la aplicación como una API desarrollada con FastAPI, SQLAlchemy y SQLite. La documentación divide el alcance en tres etapas: cotización, procesamiento de pago y emisión, y control de acceso.

2. Necesidad

La gestión de un evento requiere relacionar el lugar con sus sectores, definir precios por sector y administrar entradas disponibles. La solución también debe distinguir una cotización de una venta: cotizar no reserva ni emite entradas.

Alcance documentado

  • Administrar eventos, lugares, sectores, precios y entradas.
  • Evitar confirmar una venta si la cotización cambió o las entradas ya no están disponibles.
  • Validar la entrada emitida y evitar que una entrada ya utilizada habilite otro acceso.

3. Objetivo

Implementar un sistema que conecte la cotización, la venta y el control de entradas, aplicando programación orientada a objetos y organizando responsabilidades con principios GRASP y SOLID.

  • Separar las peticiones HTTP de las reglas de negocio y del acceso a datos.
  • Representar lugares, sectores, eventos, precios, ventas y entradas mediante entidades relacionadas.
  • Proteger el flujo de emisión y acceso con validaciones de disponibilidad, pago y estado de la entrada.

4. Organización de la solución

El código divide la solución en capas con responsabilidades diferenciadas:

  1. Rutas: reciben las solicitudes y traducen errores de la aplicación a respuestas HTTP.
  2. Servicios: contienen las reglas de catálogo, cotización, pago y acceso.
  3. Repositorios: concentran las consultas y escrituras de persistencia con SQLAlchemy.
  4. Modelos y esquemas: representan entidades persistidas y datos de entrada y salida de la API.
  5. Inyección de dependencias: conecta servicios con repositorios y dependencias de FastAPI.

5. Decisiones de diseño y desarrollo

La estructura observada en el repositorio prioriza la separación de responsabilidades y la validación del flujo de negocio:

  • El servicio de cotización comprueba cantidad, disponibilidad y precio sin reservar entradas.
  • El servicio de pago verifica cliente, precio cotizado y disponibilidad antes de invocar la pasarela simulada.
  • La confirmación de una venta y emisión de entradas se realiza en una transacción de base de datos.
  • El control de acceso verifica código QR, pago, estado de la entrada y fecha local del evento; una entrada utilizada no se vuelve a admitir.
  • Las decisiones de negocio se distribuyen entre servicios y repositorios, con contratos e inyección de dependencias descritos en el proyecto.

6. Funcionalidades verificadas

  • Crear lugares y sectores, y configurar eventos con precios por sector.
  • Generar entradas disponibles al crear un evento y cotizar entradas según cantidad y sector.
  • Procesar una venta mediante una pasarela de pago simulada; ante la aprobación, registrar la venta y emitir entradas con código QR.
  • Rechazar el pago simulado sin registrar la venta ni emitir entradas.
  • Validar el acceso con el código QR de una entrada pagada y emitida, y marcarla como utilizada.
  • Rechazar entradas inválidas, no pagadas, ya utilizadas o que no correspondan a la fecha local del evento.

La documentación del repositorio incluye pruebas automatizadas para las etapas de cotización, pago y control de acceso.

Límite del prototipo

El pago está simulado; el proyecto no realiza cobros reales ni se presenta como un servicio comercial.

7. Aprendizajes

El alcance documentado permite trabajar sobre la relación entre el modelo del dominio y las responsabilidades de cada capa:

Modelado del dominio

Relacionar lugares, sectores, eventos, precios, ventas y entradas para expresar el flujo de gestión de entradas.

Separación de responsabilidades

Distinguir el manejo de peticiones, las reglas de negocio y la persistencia facilita ubicar y probar cada comportamiento.

Estados y validaciones

La cotización, la emisión y el acceso requieren comprobar disponibilidad y estado de las entradas en cada etapa.
